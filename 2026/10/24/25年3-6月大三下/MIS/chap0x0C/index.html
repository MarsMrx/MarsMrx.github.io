实验十一：基于 boofuzz 的 CVE-2022-30024 漏洞发现实践

实验环境

  • Ubuntu
  • boofuzz

实验任务

  • 完成实验一：使⽤ boofuzz 尝试发现 CVE 2022-30024 漏洞

要求:

  • 完成针对 CVE-2022-30024 漏洞进⾏模糊测试的 boofuzz 脚本
  • 运⾏该 boofuzz 脚本，并尝试发现 CVE-2022-30024 漏洞
  • 捕获模糊测试过程中的所有完整通信流量，分析并从其中找出是哪⼀条数据报⽂导致了⽬标固件崩溃？并给出推断理由

注意事项

  1. 尝试在 boofuzz 脚本中定义要进行模糊测试的协议格式
    在定义协议格式的时候，不要携带攻击负载
  2. 尝试在 boofuzz 脚本中定义要进行变异的字段
    最好不要针对性只模糊测试一个字段，需要假设你在不知道这个漏洞的情况下进行挖掘
  3. 尝试在 boofuzz 脚本中定义认证字段
    判断是否需要先完成登录授权才能利用漏洞
  4. 尝试在 boofuzz 脚本中定义异常监控方法
    如何判定触发漏洞

实验内容

CVE-2022-30024

这是一个基于栈的缓冲区溢出，存在于二进制程序httpd（提供web服务）的ipAddrDispose函数中。漏洞发生在将 GET 请求的参数值分配给栈变量的过程中，该过程允许用户向栈内存中输入大量数据，而这些数据攻击者可控
参数从PingIframeRpm接口传递，溢出参数位置是ping_addr，影响ipAddrDispose函数

boofuzz

boofuzz是针对Session进行模糊测试的,然后定义请求包，请求包的构成分为三个单位：包(Message)、块(Block)以及原语(Primitives)

实验一：使用 boofuzz 尝试发现 CVE-2022-30024 漏洞

1.环境准备

使用之前的基于docker的漏洞复现环境，准备好漏洞环境TP-LINK仿真的固件

访问浏览器界面，获取cookie和登录后浏览器跳转链接中的认证字段

编写模糊测试脚本

  • 此处设置了多个变异字段fuzzable=False,因为时间原因，多个变异字段的测试用例太多，运行过程中，各种因素不太稳定。所以有点上帝视角只对ping_addr字段进行了测试。当然可以设置fuzzable=True来进行多个变异字段进行测试

2.进行模糊测试

测试过程中，出现了check Failed:Empty response，目标连接断开，逐渐无响应，在浏览器上查看，发现出现了crash的测试用例，这里看到的发送的请求中ping_addr是一串b，跟之前手动复现漏洞时所用的poc类似，推测是缓冲区溢出导致了目标崩溃

3.流量分析
使用wireshark分析捕获的流量包，过滤后，看到那条导致连接中断的http流量包

  • 在它之前存在，有tcp三次握手建立连接的流量
  • 在它之后，tcp连接发生了四次挥手断开连接

具体查看http流量包，发现了触发漏洞的ping_addr

思考(扩展)

1.如果你在不知道漏洞存在于哪个固件的哪个接口的情况下，你应该如何挖掘未知漏洞？你的思路是什么？
通过“信息收集 → 接口探测 → 协议分析 → 漏洞验证”四步流程挖掘潜在漏洞：

  • 信息收集：使用 Nmap 扫描端口、WhatWeb 指纹识别，并结合 CVE 数据库和 GitHub 分析已有安全问题；
  • 接口探测：借助 Wireshark 抓包、Scapy 协议重放，识别潜在 Web/API 接口；
  • 模糊测试：利用 Burp Suite、boofuzz 或 AFLNet 对 HTTP 参数、Cookie、二进制输入等字段进行变异测试；
  • 漏洞验证：结合 GDB 调试器定位异常，结合业务逻辑挖掘越权、信息泄露等漏洞。

2.你认为在你刚刚的思路中，难点或者挑战是什么？

  • 资产隐藏深：存在非标准端口、自定义协议等，攻击面难以全面覆盖；
  • 测试复杂性高：协议逆向与模糊测试用例构造难度大，存在误报/漏报风险；
  • 验证门槛高：需识别服务崩溃类型或理解复杂业务逻辑以确认漏洞。

3.你认为这些难点或者挑战可能可以如何解决？

  • 资产补全：结合 Nmap 脚本和蜜罐部署，结合被动流量分析发现隐藏服务；
  • 测试提效：借助 Frida 等工具动态追踪协议结构，结合 AI 辅助生成用例，并通过 AFL 等工具分析覆盖率优化测试路径；
  • 验证辅助：构建 Docker 仿真环境 + 自动化脚本辅助分类漏洞，参考社区漏洞样本提升验证效率和准确性。

问题与解决

1.因为环境问题，我的漏洞复现的环境中，在web页面输入完用户名和密码之后需要等待2分钟左右才会出现新的带有认证字段的跳转链接，所以基于request+正则匹配的方式无法得到那个字段。图中所示，是curl命令的响应输出中，有一段浏览器重定向到http://192.168.0.1的js代码，正常需要等待约2分钟，才会得到最终的跳转链接。但是request只能处理服务器返回的原始 HTML 内容，不会执行其中的 JavaScript。所以放弃了从登录开始的fuzz，选择手动获取cookie和认证字段之后，进行模糊测试。


总结就是常规HTTP请求获取无法在当前任务中获取完整的有效URL。可能的解决办法，采用Selenium模拟浏览器的行为(未尝试)
2. 尝试利用boofuzz官方提供的监控程序，运行process_monitor_unix.py,但是遇到了很多问题，还未解决
